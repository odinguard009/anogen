# Anogen: private AI novel engine (vendor-neutral instructions)

This file is the single source of truth for ANY AI that operates this repo (Claude, ChatGPT/Codex, Gemini, etc.). CLAUDE.md only points here. Read engine/sop.md and engine/PORTABILITY.md as well.

Owner: Odin (Indonesian; not a coder). Talk to him in Indonesian: concise, direct, no flattery, no fabrication, phone-friendly. Stories are written in English at LEARNER LEVEL (see story/style/profile.md, section LEVEL). The owner never touches code: you run every command, commit and push.

Words used here (LOCKED SETTING 13: agents are never spawned; the orchestrator performs each role itself): "agent" = the role being performed (a sequential stage of the one main session, never a separate AI run). "strong tier" / "standard tier" = informational labels from engine/models.json; the single main session uses its own model for every role. The "orchestrator" = the AI the owner talks to; it runs scripts, performs every role itself, commits and sends files.

## START HERE (any AI, every session; 2 minutes)
1. Run `python3 tools/start.py`. It prints the active novel, git state, HOLD, lock, what is due, validation errors and a NEXT line. Do what NEXT says. If it says HOLD or "no batch is running", write nothing until the owner orders it.
2. Talk to the owner in Indonesian, short. Write stories in English at learner level. Never invent facts: if a tool or file does not say it, say you did not verify it.
3. Never overwrite canon, never start sub-agents or parallel runs, never turn on the schedule, never lower the 2000-word minimum, never pad.
4. Work one role at a time under `tools/lock.py`. After any chapter edit run `python3 tools/check_chapter.py <file>`; before committing run `python3 tools/validate.py 1-N` (ERROR = a rule is broken; fix it, do not argue). Commit and push with `python3 tools/save.py "msg" --trailer "..."` (use `git add -A` first for new files).
5. Edited a chapter that the critic already reviewed? Re-review it and run `engine_state.py rereview N ...`. Otherwise the engine will block new writing.
6. Finished? `python3 tools/test_tools.py` and `python3 tools/policy_check.py` must pass; report in 3-6 lines, naming what you did NOT verify.

### Known failure modes of arc 1 and the guard that now stops each one
| What went wrong | Guard (automatic) |
|---|---|
| A file with mixed or broken encoding crashed the context pack | `common.read` tolerates it; `save.py` rewrites story/ops/chapters files as clean UTF-8 with LF line endings |
| State/ledger files grew until the writer's context was cut off | `story/bible/state.md` stays compact (full log goes to `archive/`); `context_pack.py` reports every truncation and the debts list shows only the next 40 chapters |
| Chapters came out short or long | `check_chapter.py`/`verify_batch.py`/`validate.py` enforce 2000-2500 words; `tools/common.py` has a hard floor of 2000 |
| Dates drifted from the calendar | the critic's DATE CHECK and the writer's date block (`story/bible/calendar.md` wins) |
| Plants and payoffs were forgotten or marked open forever | `tools/debts.py` (used by validate): an open debt with no `due:` number, or whose every due chapter has passed, is an ERROR |
| The outline promised a first-use label the chapter never used | `validate.py` ERROR "outline promises **[Label]**..." (write "not used yet" after a label in the outline when it must NOT appear) |
| Same session wrote and judged its own work | accepted limit (locked setting 13); the guards above are scripts, not opinion. Use the advisor consult (if the host has one) on the last five chapters of each arc, before an arc EPUB. Say so in the report; never claim an independent review |
| The same audit proposal (A1: word floor) came back five audits in a row and nothing changed | a proposal that repeats in two audits is a rule gap: turn it into a check or a locked setting, or ask the owner; never just re-write it |
| Glued words ("andbuttoned", "stood1") and tiny typos slipped through | `check_chapter.py` flags missing-space tokens; proofread separately from drafting |
| Unsure whether push works; reading-page step skipped | `start.py` shows git state and the recorded reading-page URL; `save.py` pushes, try it once at session start |
| Variety log picks contradicted the outline | NOT yet guarded: the outline wins; override the pick by hand and note it in `ops/decisions.md` |
| Old reports and drafts piled up and confused the next AI | history lives in git and `ops/decisions.md`; do not keep dead files in the tree (delete them, git remembers) |

## Production flow (strictly sequential: ONE role at a time, never parallel; NO SUB-AGENTS, see locked setting 13: every step below that mentions an agent is performed by the orchestrator itself, inline)
0. `python3 tools/engine_state.py next` -> `writer_range` (at most 5 chapters; clamped before any existing chapter, see `gap_note`), `critic_pending` (only set when a critic range of 10 chapters is due; `critic_waiting` otherwise), `critic_changed_after_review`, `audit_with_critic`, `audit_due_at`. If `lock.py status` is busy, start no role stage.
1. If the outline lacks the chapters or story/inbox.md has ideas: development editor first (strong tier, under the lock).
2. WRITER: `python3 tools/lock.py acquire write --owner writer`; run the writer stage yourself (standard tier). Prompt = engine/batch-writer-prompt.md + "Your range: chapters A-B." + the commit trailer lines (see engine/PORTABILITY.md). When it ends: `lock.py release write --owner writer`; log its usage with `python3 tools/usage_log.py add --role writer --range A-B ...` (token counts only if the host reports them; otherwise omit, never guess); verify with `git log`, `git status`, `python3 tools/verify_batch.py A-B` and `python3 tools/validate.py A-B` (ERROR/WARNING/INFO report; ERRORs must be fixed); if it died (quota): `engine_state.py batch-stop --reason "..."`, commit what exists, report.
3. CRITIC (+ AUDIT), once per 10 chapters (owner order 2026-11-25: critic per 10 chapters, i.e. after every second writer batch; replaces the earlier "after each 5-chapter batch"): run it only when `critic_pending` is set (it is, when 10 chapters are ready, when a batch ends, or at arc end). First `python3 tools/verify_batch.py A-B` (deterministic go/no-go; fix or retry the writer on problems). Then `lock.py acquire critic --owner critic`; run the critic stage yourself (strong tier). Prompt = engine/batch-critic-prompt.md + "Your range: A-B." (use `critic_pending`; add "Audit duty: yes" when `audit_with_critic` or `audit_due_at` is set). The critic runs `tools/prepass.py` first. Then `lock.py release critic --owner critic`; only if `git log` shows the "critic pass chapters A-B" commit: `engine_state.py mark critic B`; if an audit commit exists: `engine_state.py mark audit B`. Chapters changed after their review (`critic_changed_after_review` = `rereview_pending`) are an editorial task that blocks `writer_range` until done: run the critic stage (strong tier, under the lock) with "Re-review only: X, Y" (no full 10-chapter pass needed; if `critic_pending` is also set, add them to that run), then record exactly those chapters with `engine_state.py rereview X Y` (it updates hashes only for the chapters listed; `mark critic` never blesses edited chapters).
4. `python3 tools/save.py "..."` for anything left; `engine_state.py next`.
5. Reading page: `python3 tools/build_reading_page.py` and publish out/reading-page.html with the host AI's page tool; record the URL in ops/reading-page.txt. If blocked, log it in ops/blocked.md.
6. NO SESSION LIMIT (owner order 2026-11-25): keep running batches until the target or `continue` is false, a quota/limit is hit, or a STOP-list case happens. State survives in ops/engine.json. Report only at the end, in 3-6 lines.
Arc end: when `next` says the arc is fully written, run the critic on `critic_pending` (all of it still unreviewed), then `arc-complete K`, `build_epub.py --arc K`, save, and send out/arc-K.epub to the owner.
All roles run as sequential stages inside the one main session (locked setting 13). The same session writes and critiques, so the critic stage relies on tools/prepass.py, tools/verify_batch.py and the written checklists.
